1 · Overview

A skill is a self-contained folder that adds tools and/or chat commands to the agent — no changes to the agent source needed.

The agent ships with a small core: browsershell. Everything else — email, filesystem, public API search — is a skill.

Skills are discovered at startup, loaded dynamically, and their tools are merged into the LLM's tool list. Disabling a skill removes its tools and commands from the running agent immediately.

Why skills? You never edit agent.py to add a capability. You write a folder, drop it in skills/, and the agent picks it up on restart (or instantly via the Skills dialog if already loaded).

The three contracts

Every skill exports up to three things from its skill.py:

ExportPurposeRequired?
SKILL Metadata dict: name, description Yes
TOOL_SCHEMAS + TOOL_CALLABLES Tools the LLM can call Optional
COMMANDS Slash commands the user can type (/email, etc.) Optional

2 · Skill anatomy

A skill is a folder. The folder name becomes the skill name unless skill.md overrides it.

man-code/
└── skills/
    └── my_skill/
        ├── skill.py       ← code: metadata + tools + commands
        └── skill.md       ← docs: frontmatter + human notes
FilePurposeRequired?
skill.py Python module. Exports SKILL, optionally TOOL_SCHEMAS, TOOL_CALLABLES, COMMANDS. Yes
skill.md Markdown with YAML frontmatter. Supplies name, description, version, author. Anything below the frontmatter is free-form docs. Optional but recommended
any other files Templates, data files, images — whatever your skill needs. Read them via Path(__file__).parent. Optional

3 · The contract

Hello World — the smallest possible skill

# skills/greet/skill.py
SKILL = {
    "name": "greet",
    "description": "Say hello.",
}

def hello(name: str = "world") -> str:
    return f"Hello, {name}!"

TOOL_SCHEMAS = [
    {
        "type": "function",
        "function": {
            "name": "hello",
            "description": "Return a greeting for a given name.",
            "parameters": {
                "type": "object",
                "properties": {"name": {"type": "string"}},
            },
        },
    },
]

TOOL_CALLABLES = {
    "hello": hello,
}

That's it. Restart the agent, and the LLM can now call hello(name="...".

Tools — what the LLM calls

A tool has two halves:

HalfWhat it isWhere it goes
Schema A JSON function signature describing the tool: name, description, parameters, which are required. TOOL_SCHEMAS (list)
Callable The Python function that actually does the work. TOOL_CALLABLES (dict)
The schema name and the callable key must match. The LLM calls hello, the loader looks up TOOL_CALLABLES["hello"], calls it with the decoded arguments.

Rules for tool functions

  • Return a string. The agent sends the whole string back to the LLM as the tool result.
  • Prefix errors with ERROR:, BLOCKED:, or NOT_FOUND:. The agent uses these prefixes to color the log red and the LLM understands the call failed.
  • Be concise. Tool results are truncated at ~4,000 chars before going to the LLM. Long outputs waste context — summarise.
  • Never raise if you can avoid it. Wrap risky code in try/except and return an error string. Uncaught exceptions still get caught by the agent, but you lose the ability to give the LLM a helpful hint.

Schema shape

{
  "type": "function",
  "function": {
    "name": "my_tool",                 # must match callable key
    "description": "One clear sentence about what this does.",
    "parameters": {
      "type": "object",
      "properties": {
        "arg1": {"type": "string", "description": "what this is"},
        "arg2": {"type": "integer"},
        "flag": {"type": "boolean", "default": False}
      },
      "required": ["arg1"]              # omit args with defaults
    }
  }
}

Supported parameter types: string, integer, number, boolean, array, object. Most providers support these six.

Chat commands — what the user types

Commands are slash-prefixed and dispatched to the skill's handler directly. They don't go through the LLM — they run instantly.

# skills/mystuff/skill.py

def _handle_ping(args: list, log) -> None:
    """args = tokens after '/ping'. log(text, tag=None) writes to the chat."""
    log(f"pong {' '.join(args)}", "dim")

def _handle_echo(args: list, log) -> None:
    log(" ".join(args) or "(empty)", "user")

COMMANDS = {
    "ping": {
        "handler": _handle_ping,
        "description": "Reply pong",
    },
    "echo": {
        "handler": _handle_echo,
        "description": "Echo back the arguments",
    },
}

User types /ping hi → agent calls _handle_ping(["hi"], log). The command name is stripped from args.

The log function

The second argument to every command handler is a logging function. It accepts a message and an optional style tag:

TagColorUse for
"user"yellow, bolduser input echoes
"agent"green, boldagent final answers
"tool"bluetool call lines
"result"purpletool results
"error"rederrors, blocks
"dim"greyinfo lines
"turn"grey italicturn counters
log() is thread-safe. Command handlers run on the main thread (they're called from on_send), but tool functions may run on a worker thread — always use log() for output, never print().

Metadata — skill.md

skill.md is optional but useful: it lets you version a skill, credit an author, and long-describe it, without touching skill.py.

---
name: my_skill
description: One-sentence summary shown in the UI and the Skills dialog.
version: 1.0.0
author: yourname
---

# my_skill

Longer docs go here. Anything after the closing `---` is free-form
Markdown. The agent ignores it — it's for humans browsing the skill.
FieldUsed where
nameRegistry key, folder name override, "Yours" column
descriptionSkills dialog, Help dialog, publish dialog
versionSkills dialog, publish dialog, update detection
authorSkills dialog, publish dialog

If skill.md is missing, the folder name is used and the description comes from SKILL["description"].

4 · Lifecycle

From boot to shutdown, here's exactly what happens:

StepWhat runs
1. Discovery loader.discover_skills() scans skills/*/skill.py. Reads skill.md frontmatter (no code executed). Used by the Skills dialog and Help.
2. Loading loader.load_skills() imports each enabled skill.py as a module. Collects SKILL, TOOL_SCHEMAS, TOOL_CALLABLES, COMMANDS.
3. Merge All schemas are merged into one list. All callables into one dict. All commands into one dict. Duplicate names — later skill wins (alphabetical order).
4. Prompt Skill SKILL["description"] values are appended to the system prompt so the LLM knows what's available.
5. Runtime LLM calls a tool → agent looks up the callable → runs it → sends result back. User types /cmd → agent finds the handler → runs it. No LLM involved for commands.
6. Toggle Disabling a skill in the Skills dialog removes it from self.disabled_skills, saves to config, and calls _reload_tools(). That re-runs steps 2–4 without restarting the agent.
Reloading is not a restart. When you toggle a skill, its module is re-imported fresh. Any module-level state (caches, connections) is lost. If your skill needs persistent state across reloads, store it in a file — never in a module-level variable.

5 · Sandbox

Every skill has access to two environment variables that tell it where it's allowed to touch the disk:

Env varValue
AGENT_WORKSPACEAbsolute path to man-code/workspace/

Read it like this:

import os
from pathlib import Path

WORKSPACE = Path(os.environ["AGENT_WORKSPACE"]).resolve()

def write_thing(name: str, content: str) -> str:
    p = (WORKSPACE / name).resolve()
    if not str(p).startswith(str(WORKSPACE)):
        return "ERROR: path escapes workspace"
    p.write_text(content, encoding="utf-8")
    return f"OK wrote {len(content)} chars"
Always validate paths. The shell tool enforces the sandbox. Tool functions do not — it's the skill author's job. A skill that writes to arbitrary paths can be tricked into overwriting system files by a malicious prompt.

The agent config file

Skills that need persistent configuration (API keys, settings) should read and write agent_config.json at the project root:

ROOT = Path(os.environ["AGENT_WORKSPACE"]).resolve().parent
CFG  = ROOT / "agent_config.json"

def load_cfg() -> dict:
    if CFG.exists():
        return json.loads(CFG.read_text(encoding="utf-8"))
    return {}

def save_cfg(c: dict):
    CFG.write_text(json.dumps(c, indent=2), encoding="utf-8")

Read the existing config, update a key, write it back. Never overwrite the whole file — the user's API keys are in there.

6 · Publishing

To share a skill with others, publish it to the registry via skill-manager.py.

  1. Make sure the skill folder contains skill.py (required) and skill.md (recommended).
  2. Sign in: python skill-manager.py register yournickname
  3. Open the GUI: python skill-manager.py, or use the CLI:
    python skill-manager.py publish skills/my_skill --name my_skill --description "..."
  4. Click Publish. The folder is zipped in memory and uploaded.

What gets uploaded

Every file inside the folder, recursively. Exclude anything you don't want in the archive — usually you want to keep the folder tidy:

  • Ignore __pycache__/, *.pyc, .git/
  • Ignore any secrets, tokens, or .env files
  • Ignore large binary assets — the max upload is 5 MB

Versioning

Republishing a skill with the same name and a new version replaces the stored archive. Users who reinstall get the new version. There's no automatic notification — bump the version in skill.md when you want to signal a change.

7 · Installing

From the store GUI:

  1. python skill-manager.py
  2. Sign in, browse, click a skill, click Install.
  3. Restart the agent, or use the Skills dialog → toggle the skill on.

From the CLI:

python skill-manager.py install my_skill

From the agent itself (once signed in): install the skill via the store, then toggle it in the Skills dialog. The agent does not auto-install skills.

8 · Examples

Common recipes

Stateless HTTP fetch

import urllib.request, json

def fetch_json(url: str) -> str:
    try:
        with urllib.request.urlopen(url, timeout=15) as r:
            data = json.loads(r.read())
        return json.dumps(data, indent=2)[:3000]
    except Exception as e:
        return f"ERROR: {e}"

Reading a template file from the skill folder

from pathlib import Path
SKILL_DIR = Path(__file__).parent

def render(template_name: str, values: dict) -> str:
    tpl = (SKILL_DIR / "templates" / template_name).read_text()
    return tpl.format(**values)

Auto-installing a dependency at first use

import importlib, subprocess, sys

_installed = set()

def ensure(pkg: str):
    if pkg in _installed:
        return
    try:
        __import__(pkg)
    except ImportError:
        subprocess.run([sys.executable, "-m", "pip",
                        "install", "--quiet", pkg], check=True)
        importlib.invalidate_caches()
    _installed.add(pkg)

Persisting state across runs

import json, os
from pathlib import Path
STATE = Path(os.environ["AGENT_WORKSPACE"]) / ".myskill.json"

def load_state() -> dict:
    return json.loads(STATE.read_text()) if STATE.exists() else {}

def save_state(s: dict):
    STATE.write_text(json.dumps(s, indent=2))

Fallback chain across multiple providers

def call_with_fallback(payload):
    errors = []
    for provider in ["https://api.a.com", "https://api.b.com"]:
        try:
            r = requests.post(provider, json=payload, timeout=20)
            r.raise_for_status()
            return r.json()
        except Exception as e:
            errors.append(f"{provider}: {e}")
    return {"error": "all failed: " + "; ".join(errors)}

9 · Debugging

Skill not loading?

SymptomCauseFix
[loader] FAILED to import 'x' Syntax error or missing dependency in skill.py Run python skills/x/skill.py manually to see the error.
Skill listed but tools don't work TOOL_SCHEMAS names don't match TOOL_CALLABLES keys Double-check the "name" field in each schema against the dict keys.
Command not found COMMANDS dict missing or malformed Every entry needs "handler" and "description". Check the log for skipping malformed command.
LLM never calls the tool Schema description too vague Rewrite the description to be explicit about when to use it, not just what it does.
Skill disappeared after toggle Toggle added it to disabled_skills in config Open the Skills dialog, toggle it back on. Or clear disabled_skills in agent_config.json.

Logging from a skill

Two options depending on context:

  • Inside a tool function: return a string. It goes to the LLM and shows in the log.
  • Inside a command handler: call log(text, tag). It goes directly to the chat.
  • Anywhere: print() writes to the console (terminal), useful for debugging but hidden from the user.

Testing without the agent

Skills are plain Python. You can import them directly:

cd man-code
python -c "import sys; sys.path.insert(0, 'skills');
           import my_skill;
           print(my_skill.my_tool(arg='value'))"
